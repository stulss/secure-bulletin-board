> ## 현재 상태 (2026-08-21): **Render + Supabase 로 배포 진행 중**
>
> 여러 무료 Java 호스트를 검토한 끝에 최종적으로 이 조합을 택했다.
>
> | 선택 | 이유 |
> |---|---|
> | **Render** (앱) | 신용카드 등록 불필요. Docker 기반이라 Spring Boot 를 그대로 올릴 수 있다. 무료 750시간/월 |
> | **Supabase** (DB) | 신용카드 등록 불필요. PostgreSQL 표준이라 이 문서에서 이미 검증한 설정을 그대로 쓴다 |
>
> **탈락한 후보와 이유**
> - Google Cloud Run — 상시 무료·슬립 없음이지만 **신용카드(결제 계정) 등록**이 필수라 제외
> - Cloudtype — MySQL 없이 MariaDB 만 제공해 드라이버를 따로 붙여야 했다. 국내 서비스라 유력했으나 Render 로 결정하며 보류
> - Vercel · Netlify — JVM 런타임이 없어 애초에 후보가 아니다
>
> **사용 패턴**: 상시 접속이 아니라 가끔 확인하는 용도라, Render 무료 플랜의 "15분 미사용 시 슬립(재기동 30~60초)"이
> 실제로는 문제가 되지 않는다. Supabase 도 1주일 미사용 시 일시정지되지만 데이터는 보존되고 대시보드에서 재개만 하면 된다.
>
> React를 제거해 **Thymeleaf 서버 렌더링 단일 스택**이므로, 배포 대상은 Spring Boot 하나뿐이다.
> 진행 상황은 이 문서 하단 "Render 배포 절차"에 실시간으로 반영한다.

## 2단계: 배포 (필요해지면)

### 배포처 — Render(앱) + Supabase(DB), 최종 확정

| 호스트 | 카드 등록 | Java | 특징 |
|---|---|---|---|
| **Render** ✅ 선택 | **불필요** | ✅ (Docker) | 15분 미사용 시 슬립, 재기동 30~60초. 무료 750시간/월 |
| Cloudtype | 불필요로 보임 | ✅ (템플릿) | 국내 서비스·한국어 문서. 매일 1회 중지. MySQL 없이 **MariaDB** 제공. Render 로 결정하며 보류 |
| Google Cloud Run | **필수** ❌ | ✅ | 상시 무료·슬립 없음. 하지만 카드 등록이 필요해 탈락 |
| Vercel · Netlify | 불필요 | ❌ **불가** | JVM 런타임이 없다. 가이드 71건을 전수 확인했고 Java 항목은 0건이었다 |

DB 는 **Supabase**(Vercel Marketplace 경유로 프로비저닝, Supavisor Session 모드 사용) 를 실제로 연결해 검증까지 마쳤다.

---

### 배포 전에 반드시 바꿔야 하는 것 3가지 — 전부 적용·검증 완료

| | 항목 | 상태 |
|---|---|---|
| ① | H2 → 외부 DB | ✅ **완료** — `application-prod.yml` 복원, PostgreSQL 드라이버 추가, **실제 Supabase 에 연결·회원가입·로그인까지 확인** |
| ② | `PORT` 환경변수 대응 | ✅ 유지 (`application.yml`) |
| ③ | 세션 쿠키 `secure: true` | ✅ **완료** — `prod` 프로파일에 적용 |

### 운영 프로파일 (`application-prod.yml`)

`SPRING_PROFILES_ACTIVE=prod` 로 활성화된다. 로컬 개발은 기존 H2 그대로이므로 영향이 없다.

| 설정 | 값 | 이유 |
|---|---|---|
| `ddl-auto` | `validate` | 엔티티와 실제 테이블이 어긋나면 기동을 거부한다. 스키마가 조용히 틀어진 채 도는 것을 막는다 |
| `open-in-view` | `false` | 뷰 렌더링 중 DB 커넥션을 붙잡지 않는다 |
| `h2.console.enabled` | `false` | 열어두면 스키마와 데이터를 웹으로 노출하는 셈이다 |
| 세션 쿠키 | `secure` + `HttpOnly` + `SameSite=Lax` | HTTPS 전용. 로컬(http)에서 켜면 로그인이 안 되므로 prod 에만 둔다 |
| `server.error.*` | 스택 트레이스·메시지 숨김 | 오류 화면으로 내부 구조가 새지 않게 한다 |
| 로그 레벨 | `WARN` (Security 포함) | 운영에서 Security 디버그 로그는 인증 관련 내부 정보를 남긴다 |

**드라이버와 방언은 고정하지 않았다.** Spring Boot 가 JDBC URL 로 드라이버를, 커넥션 메타데이터로 방언을 알아낸다.
덕분에 **PostgreSQL 과 MySQL 중 무엇을 붙이든 설정 파일을 고칠 필요가 없다.**

> ⚠️ 그래서 `application.yml`(로컬)에서도 `driver-class-name`·`database-platform` 을 **지정하면 안 된다.**
> 지정하면 그 값이 prod 에도 남아 PostgreSQL URL 에 H2 드라이버를 물리려다 기동이 실패한다. 실제로 이 문제를 겪고 제거했다.

### DB — Supabase (PostgreSQL)

Vercel Marketplace 를 통해 Supabase 프로젝트를 만들었다. 접속 정보는 supabase.com 대시보드가 아니라
**Vercel 프로젝트 → Storage 탭 → 해당 DB → `.env.local` 보기**에서 나온다.

> ⚠️ **이 DB 가 연결된 Vercel 프로젝트(`secure-bulletin-board`)는 삭제하지 말 것.**
> Marketplace 로 프로비저닝한 스토리지는 그 프로젝트에 종속된다. 프로젝트를 지우면 DB 도 함께 사라질 수 있다.
> 이 Vercel 프로젝트 자체에 Spring Boot 를 올리는 것은 아니다 — Storage(DB) 용도로만 남겨둔다.

**연결 시 반드시 `POSTGRES_URL_NON_POOLING` 값을 쓴다.** 호스트가
`aws-0-<region>.pooler.supabase.com` 형태이고 포트가 `5432`면 Supavisor 의 **Session 모드**로,
이 앱처럼 세션 인증으로 커넥션을 길게 붙잡는 구조에 맞는다. 포트 `6543`(Transaction 모드)은 쓰지 않는다.

`postgres://user:pass@host:5432/db?sslmode=require` 형식을 Render 환경변수 3개로 나눠 담는다 (아래 "환경변수" 참고).

스키마는 커밋 `b0a2025` 에서 복원했다:

- `src/main/resources/db/schema-postgres.sql` — 손으로 쓴 것이 아니라 엔티티에서 Hibernate 가 생성한 DDL.
  엔티티를 고치면 다시 생성해야 `validate` 가 통과한다 (방법은 이 문서 맨 아래 "스키마 재생성")

### 검증한 것 (2026-08-21)

설정만 써두고 끝내지 않고 실제 Supabase 에 붙여 확인했다.

| 확인 | 결과 |
|---|---|
| `PORT` 미설정 / `PORT=9090` | 각각 8080·9090 에서 응답, 반대쪽 포트는 비어 있음 |
| Supabase 최초 연결 (`ddl-auto=update`, 1회) | 5.2초 만에 기동, 스키마 생성 성공 |
| **재기동 (`ddl-auto=validate`, 실제 배포 설정)** | **통과** — 엔티티와 원격 테이블이 정확히 일치 |
| 실제 회원가입 → Supabase 저장 | 302 (성공) |
| 실제 로그인 → 세션 인증 | `{"username":"renderuser1"}` |
| CSP 헤더 | `prod` 프로파일에서도 정상 적용 |
| Dockerfile 의 jar 선택 로직 (`find ... ! -name '*-plain.jar'`) | 실행 가능한 jar 1개만 정확히 선택됨, 매니페스트 확인 |
| `java -XX:MaxRAMPercentage=75 -jar app.jar` (Dockerfile 과 동일한 실행 방식) | 정상 기동, `/api/posts` 200 |
| 로컬 기본 프로파일(H2) 회귀 | 정상, JUnit 36건 전부 통과 |

> Docker Desktop 이 로컬에서 불안정해(설치 폴더가 비어 재설치 필요) **이미지 자체의 빌드는 로컬에서 확인하지 못했다.**
> 대신 Dockerfile 이 실행하는 정확한 커맨드(jar 선택 로직·JVM 플래그)를 그대로 로컬에서 재현해 검증했다.
> 이미지 빌드 자체는 Render 가 push 시점에 서버에서 수행하므로 최종 검증은 실제 배포 로그로 확인할 것.

## Render 배포 절차

### 3-1. 사전 조건 — 전부 완료

- GitHub 저장소: **https://github.com/stulss/secure-bulletin-board** (`main`, `v0.0.1` push 완료)
- `gradlew` 실행 권한 `100755` 등록 완료, `gradle-wrapper.jar` 커밋 완료
- `Dockerfile`, `.dockerignore` 저장소 루트에 추가 완료
- DB: Supabase 연결 검증 완료 (위 "검증한 것" 참고)

### 3-2. Render 서비스 생성

1. Render 대시보드 → **New** → **Web Service**
2. GitHub 저장소 `stulss/secure-bulletin-board` 연결, 브랜치 `main`
3. **Language**: `Docker` 선택 (저장소 루트의 `Dockerfile` 을 자동으로 찾는다)
4. **Instance Type**: `Free`
5. Region 은 가까운 곳(예: Singapore)으로 — 한국 리전은 없다

Dockerfile 안에 시작 명령이 이미 들어있으므로 Build/Start Command 를 따로 입력할 필요는 없다.

### 3-3. 환경변수

서비스 생성 화면 또는 생성 후 **Environment** 탭에서 추가한다. 비밀번호를 코드나 설정 파일에 쓰지 않는 이유가 이것이다.

```
SPRING_PROFILES_ACTIVE = prod
DB_URL                  = jdbc:postgresql://aws-0-ap-northeast-2.pooler.supabase.com:5432/postgres?sslmode=require
DB_USER                 = postgres.<프로젝트 참조 ID>
DB_PASSWORD             = (Vercel Storage 탭의 POSTGRES_URL_NON_POOLING 에서 가져온 값)
```

`PORT` 는 Render 가 자동으로 주입하므로 직접 설정하지 않는다.

### 3-4. 접속 확인

`context-path: /api` 때문에 **루트로 들어가면 404** 다. 실제 진입점은:

```
https://<서비스명>.onrender.com/api/posts
```

### 3-5. 무료 플랜에서 알아둘 것

- **15분 미사용 시 슬립**된다. 다음 요청이 오면 재기동에 30~60초가 걸린다 — 상시 접속이 아니라 가끔 확인하는 용도라 문제되지 않는다
- 무료 750시간/월 — 인스턴스 1개를 한 달 내내 켜둬도 약 744시간이라 한도 안에 들어온다
- Supabase 도 1주일 미사용 시 프로젝트가 일시정지된다. **데이터는 보존**되며 Vercel/Supabase 대시보드에서 재개 버튼만 누르면 된다

## 참고: 스키마 재생성

엔티티를 고치면 `ddl-auto: validate` 가 기동을 거부한다. 그때 스키마 SQL 을 다시 만든다.
손으로 고치지 말고 아래처럼 Hibernate 가 생성하게 할 것 — 손으로 쓰면 미묘하게 어긋나서 `validate` 가 계속 실패한다.

`src/test/java/com/securitybulletin/SchemaExportTest.java` 를 임시로 만들어 실행한다.

```java
@SpringBootTest
@TestPropertySource(properties = {
    "spring.jpa.hibernate.ddl-auto=none",
    "spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect",  // 또는 MySQLDialect
    "spring.jpa.properties.jakarta.persistence.schema-generation.scripts.action=create",
    "spring.jpa.properties.jakarta.persistence.schema-generation.scripts.create-target=build/schema-postgres.sql",
    "spring.jpa.properties.hibernate.hbm2ddl.delimiter=;"
})
class SchemaExportTest {
    @Test void exportSchema() { }   // 컨텍스트가 뜨는 것만으로 스크립트가 생성된다
}
```

```bash
./gradlew test --tests "com.securitybulletin.SchemaExportTest"
```

`build/schema-*.sql` 이 생성되면 `src/main/resources/db/` 로 옮기고, **임시 테스트는 지운다.**

## 부록: 다른 배포처를 쓸 경우

Render 대신 선택할 수 있는 다른 경로. 지금은 쓰지 않지만 참고용으로 남겨둔다.

### A. Google Cloud Run — 슬립이 아예 없다

카드 등록만 감수하면 이쪽이 더 낫다. 상시 무료(월 200만 요청)이고 요청이 없으면 0으로 줄어들 뿐 슬립·재기동 지연이 없다.

### 빌드 방식 — Java 17을 명시해야 한다

`gcloud run deploy --source .`는 Dockerfile 없이 버들팩으로 빌드해준다. 다만 **버들팩의 기본 Java 버전이 낮아** 그대로 두면 빌드가 깨진다. 프로젝트 루트에 `project.toml`을 만든다:

```toml
[[build.env]]
name = "GOOGLE_RUNTIME_VERSION"
value = "17"
```

> Dockerfile을 직접 쓰고 싶다면 `./gradlew bootBuildImage`로 이미지를 만들어도 된다.
> 버들팩 쪽이 관리할 파일이 적어 이 프로젝트에는 더 맞는다.

#### 2-2. DB 준비 (Supabase 또는 Neon)

1. 프로젝트 생성 → **JDBC 연결 문자열** 확인
2. `src/main/resources/db/schema-postgres.sql` 을 한 번 실행해 테이블을 만든다
3. 로컬 H2 데이터는 옮길 필요 없다 (테스트 데이터일 뿐이다)

> **Supabase 무료 티어 주의**: 약 1주일간 접속이 없으면 프로젝트가 일시정지되고, 대시보드에서 수동으로 재개해야 한다.
> 포트폴리오 링크를 오래 방치했다가 면접 직전에 확인하는 상황이라면 이 점을 기억할 것.
> 이게 걸리면 **Neon**(서버리스 Postgres)이 Cloud Run의 스케일 투 제로와 궁합이 더 좋다.

#### 2-3. 배포

```bash
gcloud run deploy secure-bulletin-board \
  --source . \
  --region asia-northeast3 \
  --allow-unauthenticated \
  --max-instances 1 \
  --set-env-vars "SPRING_PROFILES_ACTIVE=prod" \
  --set-env-vars "DB_URL=jdbc:postgresql://...,DB_USER=...,DB_PASSWORD=..."
```

- `--allow-unauthenticated`: 누구나 접속 가능하게 한다 (공개 게시판이므로)
- `--max-instances 1`: **세션 인증이라 인스턴스가 늘면 세션이 흩어진다.** 포트폴리오 트래픽에서는 1개로 고정하는 편이 안전하다
- 비밀번호를 명령줄에 직접 넣기 싫다면 **Secret Manager**를 쓰고 `--set-secrets`로 주입한다

#### 2-4. 접속 주소 주의

`context-path: /api`이므로 **루트(`https://.../`)로 들어가면 404**가 뜬다. 실제 진입점은:

```
https://<서비스주소>/api/posts
```

포트폴리오에 링크를 걸 때 `/api/posts`까지 포함해야 한다.
루트로도 들어가게 하려면 `context-path`를 없애야 하는데, 그러면 Postman 콜렉션과 문서의 경로를 전부 바꿔야 하므로 **링크에 경로를 포함하는 편이 간단하다.**

---

### JVM 메모리

무료 티어는 메모리가 512MB~1GB인데 **JVM만 200-300MB를 쓴다.** Cloud Run 기본값(512MB)으로도 뜨지만, 여유를 두려면:

```bash
--memory 1Gi --set-env-vars "JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75"
```

메모리를 올리면 무료 한도(GB-초)를 더 빨리 소진하지만, 포트폴리오 수준의 트래픽에서는 문제되지 않는다.

### B. Cloudtype — 국내 서비스, 한국어 문서

카드 등록 없이 되는 것으로 보였으나 MySQL 대신 MariaDB 만 제공해 이번엔 보류했다. 시도한다면:

- 시작하기 → **데이터베이스** → **PostgreSQL** 또는 **MariaDB** 선택 (MySQL 은 없다. 검색 결과의 phpMyAdmin 은 DB 가 아니라 관리 도구이니 고르지 말 것)
- 앱 → **Spring Boot** 템플릿 → 이 저장소 연결. 빌드 `./gradlew clean bootJar`, 실행 `java -jar build/libs/secure-bulletin-board-1.0.0.jar`, 포트 `8080`
- DB 서비스명이 곧 내부 호스트명이 된다 (`postgresql-prod:5432` 형태)
- **매일 1회 자동 중지**되지만 DB 데이터는 유지된다(공식 문서 명시). 다만 자동 백업은 없다

## 배포 후 체크리스트

- [x] `ddl-auto`가 `validate`인가 — 로컬에서 실제 Supabase 로 확인
- [x] 세션 쿠키 `secure: true` / H2 콘솔 차단 — `prod` 프로파일 적용, CSP 헤더 응답에서 확인
- [x] `SPRING_PROFILES_ACTIVE=prod` 를 실제로 넣었는가 — 로컬 검증에서 확인. **Render 환경변수에도 반드시 넣을 것**, 빠뜨리면 H2 인메모리로 뜬다
- [x] 스키마가 DB와 맞는가 — `ddl-auto=update` 로 1회 생성 후 `validate` 재기동 통과
- [x] DB 비밀번호가 코드·설정 파일이 아니라 환경변수로만 들어가는가 — 커밋된 파일에는 플레이스홀더만 있다
- [x] 회원가입 → 로그인이 실제 배포용 DB에서 동작하는가 — 로컬에서 Supabase 대고 확인 완료
- [ ] Render 배포 후 **타인 글 수정 차단(403)** 이 실제 배포 환경에서도 동작하는가 — 로컬 회귀로는 확인됐으나 배포 URL 에서 재확인 필요
- [ ] Postman 콜렉션을 Production 환경(`baseUrl`을 Render 배포 주소로)으로 돌려 **39개 단언이 전부 통과**하는가
- [ ] 배포 URL에 대고 **ZAP 스캔을 다시** 돌렸는가 — HTTPS가 붙으면 로컬과 결과가 달라진다
- [ ] 포트폴리오 링크에 `/api/posts` 경로가 포함돼 있는가

> **CORS 설정은 필요 없다.** React를 제거해 브라우저가 다른 출처로 요청할 일이 없어졌다.
> 화면과 API가 같은 출처에서 서빙되므로 CORS를 열 이유가 없고, 열지 않는 편이 안전하다.
