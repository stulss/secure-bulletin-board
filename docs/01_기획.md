## 1. 프로젝트 배경 및 목적

### 왜 이 프로젝트를 기획했는가
- **취업 포트폴리오 목적**: 국비지원 과정 수료 후 채용 시장에서 백엔드/보안 역량을 증명할 프로젝트가 필요하다. "게시판 CRUD"는 흔한 포트폴리오지만, 여기에 **인증/인가 + OWASP Top 10 방어**를 얹으면 단순 CRUD 이상의 실무형 프로젝트가 된다.
- **보안 기술 습득 목적**: Spring Security의 인증(Authentication)·인가(Authorization) 파이프라인을 직접 구성해보지 않으면 "설정만 붙여넣는" 수준에 머무른다. 세션 기반 인증, `@PreAuthorize`를 통한 메서드 단위 접근 제어, CSRF 토큰, BCrypt 해싱을 직접 구현하며 각 방어 기법이 **왜 필요한지**를 코드 레벨에서 이해하는 것이 목적이다.

### 이 프로젝트로 해결하려는 문제
- 국비 교육 과정에서 만든 게시판 예제 다수가 **평문 비밀번호 저장, XSS 무방비, 인가 로직 부재**(다른 사람 글을 URL만 바꿔 수정/삭제 가능) 상태로 끝난다. 이 프로젝트는 "동작하는 게시판"과 "안전한 게시판"의 차이를 명시적으로 보여주는 것을 목표로 한다.
- 구체적으로 아래 세 가지 흔한 취약점을 게시판이라는 익숙한 도메인 위에서 직접 재현하고 방어한다.
  1. 비밀번호 평문 저장 → BCrypt 해싱
  2. 게시글 본문에 스크립트 삽입(XSS) → 입력값 필터링 + Thymeleaf 자동 이스케이프
  3. 검색/조회 파라미터 조작(SQL Injection) → JPA 파라미터 바인딩

## 2. 타겟 사용자

### 주요 사용자
| 사용자 유형 | 설명 |
|---|---|
| 일반 사용자 (회원) | 회원가입 후 게시글을 작성·조회·수정·삭제하는 주 사용자 |
| 관리자 (선택 확장) | 4주 MVP 범위 밖. [12. 향후 확장 계획]에서 별도 역할로 다룬다 |
| 비회원 (게스트) | 로그인 없이 글 목록·상세는 열람 가능, 작성/수정/삭제는 로그인 필요 |

### 사용자 시나리오
1. 방문자는 로그인 없이 게시글 목록과 상세 내용을 열람할 수 있다.
2. 사용자는 이메일과 비밀번호로 회원가입하고, 가입 즉시 로그인 화면으로 이동한다.
3. 사용자는 로그인 후 게시글을 작성할 수 있으며, 작성된 글은 목록 최상단에 노출된다.
4. 사용자는 **본인이 작성한 글만** 수정·삭제할 수 있다. 타인의 글 수정/삭제 URL에 직접 접근하면 403으로 거부된다.
5. 사용자는 로그아웃하면 세션이 즉시 만료되고, 이후 인증이 필요한 페이지 접근 시 로그인 화면으로 리다이렉트된다.
6. 공격자가 게시글 본문에 `<script>` 태그를 넣어 등록을 시도하면, 저장 시점 또는 출력 시점에 무해화되어 스크립트가 실행되지 않는다.
7. 공격자가 로그인 폼이나 검색창에 `' OR '1'='1` 같은 SQL 구문을 입력해도 쿼리가 구조적으로 변조되지 않는다.

## 3. 주요 기능 명세서

| 분류 | 기능 | 설명 |
|---|---|---|
| 회원 관리 | 회원가입 | 이메일 중복 검사, 비밀번호 규칙 검증(최소 8자, 영문+숫자 조합) 후 BCrypt 해싱하여 저장 |

| 회원 관리 | 비밀번호 변경 | 현재 비밀번호 재확인 후 신규 비밀번호로 재해싱 |
| 게시글 관리 | 글 목록 조회 | 페이징 처리(Pageable), 최신순 정렬 |
| 게시글 관리 | 글 작성 | 로그인 사용자만 가능, 제목·본문 필수값 검증 |
| 게시글 관리 | 글 수정 | 작성자 본인만 가능 |
| 게시글 관리 | 글 삭제 | 작성자 본인만 가능, soft delete가 아닌 실제 삭제(MVP 기준) |
| 게시글 관리 | 글 상세 조회 | 비회원도 열람 가능 |
| 권한 제어 | 본인 글만 수정/삭제 | 서비스 계층에서 `post.getAuthor().equals(currentUser)` 검증, 불일치 시 403 |
| 권한 제어 | 타인 글 접근 제한 | 수정/삭제 API는 작성자 일치 여부를 서버에서 재검증(클라이언트 숨김 버튼만으로 방어하지 않음) |
| 보안 기능 | 비밀번호 암호화 | `BCryptPasswordEncoder` (기본 strength 10) |
| 보안 기능 | CSRF 토큰 검증 | Spring Security 기본 CSRF 필터 활성화, Thymeleaf 폼에 토큰 자동 삽입 |
| 보안 기능 | XSS 방어 | 서버 측 입력값 필터링(허용 태그 화이트리스트 또는 전체 이스케이프) + Thymeleaf `th:text` 자동 이스케이프 |
| 보안 기능 | SQL Injection 방어 | Spring Data JPA(파라미터 바인딩) 사용, 네이티브 쿼리 문자열 조합 금지 |

## 4. 시스템 아키텍처

### 기술 스택
| 영역 | 기술 |
|---|---|
| Backend | Java 17, Spring Boot 3.x, Spring Security, Spring Data JPA |
| Frontend | HTML5, CSS3 (Bootstrap 5, 로컬 서빙), Thymeleaf 서버 렌더링 |
| Database | H2 인메모리 (로컬 전용) |
| Build Tool | Gradle 9.5.1 (Wrapper 포함) |
| 테스트 | JUnit 5, Spring Security Test, `@SpringBootTest`, Postman/newman, OWASP ZAP |

> **DB 결정의 변천 (최종: H2 로컬 전용)**
> 1. 최초 계획: H2(개발) / MySQL(운영) 이원화
> 2. 변경: 방언 차이로 인한 뒤늦은 버그를 없애려 **Supabase 관리형 PostgreSQL**을 개발·운영 공용으로 쓰기로 결정
> 3. **최종 (2026-08-21)**: **배포를 하지 않기로 하면서 H2 인메모리만 사용**한다. 무료 Java 호스트가 신용카드 등록을 요구해 배포를 접었다 — 경위는 [docs/05_배포.md](05_배포.md) 참고
>
> 배포를 재개하면 PostgreSQL/MySQL 설정과 스키마 SQL을 커밋 `b0a2025`에서 되살릴 수 있다.
> 그때도 **Supabase의 Auth/RLS는 쓰지 않는다** — 이 프로젝트의 목적이 Spring Security로 인증/인가를 직접 구현하는 것이므로, DB는 순수 저장소 역할만 한다.
> DB 접속 정보는 커밋하지 않고 환경변수로 주입한다.

### 아키텍처 (MVC 패턴 기반)

```
[Browser]
   │  HTTP 요청 (폼 제출 / CSRF 토큰 포함)
   ▼
┌─────────────────────────────────────────────┐
│  Spring Security Filter Chain                │
│  - CSRF 검증 → 인증(Authentication) → 인가(Authorization) │
└─────────────────────────────────────────────┘
   │  인증/인가 통과분만 통과
   ▼
┌───────────────┐   ┌────────────────┐   ┌───────────────┐
│  Controller    │──▶│  Service        │──▶│  Repository    │
│ (요청/응답,    │   │ (비즈니스 로직,  │   │ (JPA, 파라미터  │
│  입력값 검증)  │   │  본인 확인 등)   │   │  바인딩)       │
└───────────────┘   └────────────────┘   └───────────────┘
   │                                             │
   ▼                                             ▼
┌───────────────┐                        ┌───────────────┐
│  Thymeleaf     │                        │  DB            │
│  View (자동    │                        │  (H2 인메모리, │
│  이스케이프)   │                        │   로컬 전용)   │
└───────────────┘                        └───────────────┘
```

- **Controller**: HTTP 요청을 받아 DTO로 매핑하고 Service를 호출한다. 인증 여부는 Security가 이미 필터링했으므로, Controller는 "누가 요청했는가(`Authentication` 객체)"만 꺼내 쓴다.
- **Service**: 게시글 작성자와 현재 로그인 사용자가 같은지 여기서 재검증한다. 이 검증을 Controller나 프론트에서만 하면 API를 직접 호출해 우회할 수 있으므로 반드시 Service 계층에 둔다.
- **Repository**: `JpaRepository` 상속만으로 CRUD를 구현해 SQL 문자열을 직접 조립하지 않는다. 동적 검색이 필요한 경우에도 `@Query`의 `:param` 바인딩만 사용한다.

## 5. 데이터베이스 설계 (ERD)

### users 테이블
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 사용자 식별자 |
| username | VARCHAR(50) | UNIQUE, NOT NULL | 로그인 ID |
| password | VARCHAR(100) | NOT NULL | BCrypt 해시 (평문 저장 금지) |
| email | VARCHAR(100) | UNIQUE, NOT NULL | 이메일 |
| created_at | TIMESTAMP | NOT NULL | 가입 일시 |
| updated_at | TIMESTAMP | NOT NULL | 정보 수정 일시 |

### posts 테이블
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, AUTO_INCREMENT | 게시글 식별자 |
| user_id | BIGINT | FK → users.id, NOT NULL | 작성자 |
| title | VARCHAR(200) | NOT NULL | 제목 |
| content | TEXT | NOT NULL | 본문 |
| created_at | TIMESTAMP | NOT NULL | 작성 일시 |
| updated_at | TIMESTAMP | NOT NULL | 수정 일시 |

### 관계
- `users` : `posts` = **1 : N** (사용자 한 명이 여러 게시글 작성)
- `posts.user_id`에 FK 제약을 걸어, 존재하지 않는 사용자 소유의 글이 생성되지 않도록 DB 레벨에서도 방어한다.

```
users (1) ──────< (N) posts
  id                  user_id (FK)
  username             title
  password             content
  email                created_at
  created_at           updated_at
  updated_at
```

## 6. API 명세서

| Method | URL | 설명 | 인증 필요 | 성공 응답 |
|---|---|---|---|---|
| POST | `/api/auth/signup` | 회원가입 | ✗ | 201 Created |
| POST | `/api/auth/login` | 로그인 | ✗ | 200 OK + 세션 쿠키 |
| POST | `/api/auth/logout` | 로그아웃 | ✓ | 200 OK, 세션 무효화 |
| GET | `/api/posts` | 글 목록 조회 (페이징) | ✗ | 200 OK |
| POST | `/api/posts` | 글 작성 | ✓ | 201 Created |
| GET | `/api/posts/{id}` | 글 상세 조회 | ✗ | 200 OK |
| PUT | `/api/posts/{id}` | 글 수정 (본인만) | ✓ | 200 OK / 403 Forbidden |
| DELETE | `/api/posts/{id}` | 글 삭제 (본인만) | ✓ | 204 No Content / 403 Forbidden |

### 컨트롤러 예시 (본인 확인이 Service로 위임되는 구조)

```java
@RestController
@RequestMapping("/api/posts")
@RequiredArgsConstructor
public class PostController {

    private final PostService postService;

    @PutMapping("/{id}")
    public ResponseEntity<PostResponse> update(
            @PathVariable Long id,
            @Valid @RequestBody PostUpdateRequest request,
            @AuthenticationPrincipal CustomUserDetails principal) {

        // 작성자 본인 확인은 Controller가 아니라 Service에서 수행한다.
        // (Controller에서만 걸러내면 Service를 직접 호출하는 다른 경로에서 우회될 수 있다)
        PostResponse response = postService.update(id, request, principal.getUserId());
        return ResponseEntity.ok(response);
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class PostService {

    private final PostRepository postRepository;

    @Transactional
    public PostResponse update(Long postId, PostUpdateRequest request, Long currentUserId) {
        Post post = postRepository.findById(postId)
                .orElseThrow(() -> new PostNotFoundException(postId));

        if (!post.getAuthorId().equals(currentUserId)) {
            throw new AccessDeniedException("본인 게시글만 수정할 수 있습니다.");
        }

        post.update(request.getTitle(), request.getContent());
        return PostResponse.from(post);
    }
}
```

## 7. 보안 요구사항

| 항목 | 적용 방식 |
|---|---|
| 인증 | Spring Security 기반 세션 인증 (`SecurityFilterChain` + `UserDetailsService`) |
| 인가 | `@PreAuthorize`(메서드 단위) + Service 계층의 소유자 확인(리소스 단위) 이중 방어 |
| 비밀번호 보호 | `BCryptPasswordEncoder`로 해싱, 평문 저장/평문 로그 출력 금지 |
| 입력값 검증 | Bean Validation(`@NotBlank`, `@Size`) + XSS 필터(허용 태그 화이트리스트) |
| CSRF | Spring Security 기본 CSRF 필터 활성화, 상태 변경 요청(POST/PUT/DELETE)에 토큰 필수 |
| SQL Injection | Spring Data JPA만 사용, 문자열 결합 쿼리(`+` 연산으로 SQL 조립) 금지 |
| HTTPS | 로컬 개발 환경 제외, 운영 배포 시 적용 (배포 방식은 [05_배포.md](05_배포.md) 참고) |
| 세션 관리 | 로그아웃 시 세션 무효화, 세션 고정(Session Fixation) 공격 방지를 위해 로그인 성공 시 세션 ID 재발급 |

### Security 설정 예시

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity(prePostEnabled = true)
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/posts", "/posts/{id}", "/api/auth/signup", "/api/auth/login").permitAll()
                .requestMatchers("/css/**", "/js/**").permitAll()
                .anyRequest().authenticated()
            )
            .formLogin(form -> form
                .loginPage("/login")
                .defaultSuccessUrl("/posts", true)
            )
            .logout(logout -> logout
                .logoutUrl("/api/auth/logout")
                .invalidateHttpSession(true)
                .deleteCookies("JSESSIONID")
            )
            .sessionManagement(session -> session
                .sessionFixation(SessionManagementConfigurer.SessionFixationConfigurer::migrateSession)
            );
            // CSRF는 기본 활성화 상태를 유지한다 (명시적으로 disable() 호출하지 않음)

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

| 3주차 | Spring Security 통합 | Security 설정 전체 적용, 세션 인증, `@PreAuthorize` + Service 계층 소유자 검증으로 권한 제어 구현 |
| 4주차 | 보안 강화 + 마무리 | XSS 필터링, CSRF 토큰 점검, BCrypt 적용 확인, JUnit/SpringBootTest 작성, OWASP ZAP 스캔, 버그 수정, 문서 정리 |

## 9. 테스트 계획

| 유형 | 도구 | 대상 |
|---|---|---|
| 단위 테스트 | JUnit 5, Mockito | Service 계층 로직 (특히 "본인 글만 수정 가능" 검증 로직) |
| 통합 테스트 | `@SpringBootTest`, `MockMvc` | API 엔드포인트 전체 (인증 성공/실패, 인가 성공/실패 케이스 포함) |
| 보안 테스트 | OWASP ZAP | XSS·SQL Injection 취약점 자동 스캔 |
| 수동 침투 테스트 | 브라우저 개발자도구 + curl | 타인 글 ID로 PUT/DELETE 직접 호출 시 403 확인, `<script>` 태그 등록 후 렌더링 확인 |

### 필수로 확인할 실패 케이스 (통과 기준)
- [ ] 비로그인 상태로 `POST /api/posts` 호출 → 401/403
- [ ] A 사용자가 B 사용자의 글 ID로 `PUT /api/posts/{B의 글 ID}` 호출 → 403
- [ ] 게시글 본문에 `<script>alert(1)</script>` 등록 후 상세 조회 → 스크립트 미실행(이스케이프된 텍스트로 렌더링)
- [ ] 로그인 폼 아이디 필드에 `' OR '1'='1` 입력 → 로그인 실패(구문 오류나 우회 없음)
- [ ] DB에 저장된 비밀번호 컬럼이 평문이 아닌 BCrypt 해시(`$2a$...` 형식)인지 확인
- [ ] CSRF 토큰 없이 `POST /api/posts` 직접 호출(curl 등) → 403

## 10. 예상 난이도 및 리스크

| 항목 | 내용 |
|---|---|
| 난이도 | 초급~중급 (Spring Security 학습 곡선이 가장 큰 변수) |
| 리스크 1 | Security 설정 오류로 정상 요청까지 막히거나, 반대로 인가 누락으로 보호돼야 할 API가 열려 있는 경우 |
| 대응 1 | 기능 하나를 구현할 때마다 "로그인 안 한 상태" / "다른 사용자로 로그인한 상태" 두 가지로 즉시 재현 테스트 |
| 리스크 2 | 세션 관리 이해 부족으로 로그아웃 후에도 이전 세션이 유효하거나, 세션 고정 공격에 노출 |
| 대응 2 | `invalidateHttpSession(true)` + 로그인 성공 시 세션 재발급(`migrateSession`) 명시적으로 설정하고, 로그아웃 후 인증 필요 페이지 재접근으로 직접 검증 |
| 리스크 3 | XSS 필터링을 과하게 적용해 정상적인 게시글 작성(예: `<`, `>` 기호 포함 텍스트)이 깨지는 경우 | 
| 대응 3 | 화이트리스트 기반 필터링(Thymeleaf 자동 이스케이프를 기본으로 하고, 별도 HTML 허용은 하지 않음)으로 범위를 좁혀 시작 |

## 11. 포트폴리오 강조 포인트

- Spring Security를 통한 인증/인가 구현 경험 — 세션 인증, 메서드 보안, 리소스 소유자 검증까지 이중 방어 구조로 구현
- OWASP Top 10 취약점(XSS, SQL Injection) 방어를 게시판이라는 구체적 도메인 위에서 재현·검증
- BCrypt를 이용한 비밀번호 암호화 저장 — 평문 비교와 차이를 DB 컬럼 값으로 직접 증명
- JPA를 통한 SQL Injection 자동 방어 — 파라미터 바인딩 원칙을 지킨 리포지토리 계층
- "완료됐다"는 주장을 자동 테스트 + 수동 침투 테스트로 이중 검증한 과정 자체([검증안내서](../검증안내서.md) 참고)
