# UI/UX 설계 — 프론트엔드 구조와 화면 명세

**관련 문서:** [README](../README.md) · [01_기획.md](01_기획.md) · [03_백엔드구조.md](03_백엔드구조.md)

> 이 문서는 [01_기획.md §3 기능 명세](01_기획.md#3-주요-기능-명세서)를 화면 단위로 풀어 쓴 것이다.
> 기술 스택은 Thymeleaf + Bootstrap 5 + 최소한의 JavaScript(폼 검증 보조용) — SPA 프레임워크는 쓰지 않는다.

---

## 1. 디자인 원칙

1. **Bootstrap 5 컴포넌트를 그대로 쓴다.** 커스텀 CSS는 색상 변수(`--bs-primary` 등) 재정의와 간격 조정 정도로 최소화한다 — 4주 안에 디자인 시스템을 새로 만드는 것은 우선순위가 아니다.
2. **모바일 우선.** Bootstrap 기본 breakpoint(`sm 576px / md 768px / lg 992px`)를 그대로 따르고, 목록·폼 모두 좁은 화면에서 세로 스택으로 무너지는지 먼저 확인한다.
3. **보안 상태를 화면에 드러낸다.** 로그인 여부, 본인 글 여부에 따라 버튼 자체가 아예 안 보이거나 비활성화된다 — 다만 이는 UX일 뿐이고 **실제 방어는 항상 서버(Service 계층)** 에서 한다 ([01_기획.md §7](01_기획.md#7-보안-요구사항) 참고). 화면에 버튼이 없다고 서버 검증을 생략하지 않는다.
4. **에러 메시지는 정보를 흘리지 않는다.** 로그인 실패 시 "아이디가 없습니다" / "비밀번호가 틀립니다"를 구분해서 보여주지 않고 **"아이디 또는 비밀번호가 올바르지 않습니다"** 하나로 통일한다 (계정 존재 여부 추측 방지).

## 2. 정보구조 (사이트맵)

```
/                      게시글 목록 (= /posts, 비로그인도 열람)
├─ /posts/{id}         게시글 상세 (비로그인도 열람)
│   ├─ /posts/{id}/edit    글 수정 (작성자만, 로그인 필요)
│   └─ (삭제는 상세 화면 버튼 → 확인 모달 → API 호출, 별도 페이지 없음)
├─ /posts/new           글 작성 (로그인 필요)
├─ /login                로그인
├─ /signup               회원가입
└─ /account/password     비밀번호 변경 (로그인 필요)
```

## 3. 공통 레이아웃

모든 페이지는 아래 뼈대를 공유한다 (Thymeleaf 레이아웃 조각 `fragments/layout.html`).

```
┌───────────────────────────────────────────────┐
│  Navbar                                        │
│  [로고] 게시판          (비로그인) 로그인 | 회원가입 │
│                        (로그인)   글쓰기 | {닉네임}▾ │
├───────────────────────────────────────────────┤
│  Flash 메시지 영역 (성공/실패 알림, 있을 때만)      │
├───────────────────────────────────────────────┤
│                                                 │
│  {{ 페이지별 본문 }}                             │
│                                                 │
├───────────────────────────────────────────────┤
│  Footer (최소: 프로젝트명, GitHub 링크)            │
└───────────────────────────────────────────────┘
```

- **Navbar 우측**은 로그인 여부에 따라 완전히 다른 메뉴를 렌더링한다 (`sec:authorize="isAuthenticated()"` / `sec:authorize="isAnonymous()"` — Thymeleaf Spring Security 확장).
- **Flash 메시지**는 로그인 실패, 글 작성/수정/삭제 성공, 권한 없음(403) 등을 리다이렉트 후 한 번만 보여주는 용도로 쓴다(`RedirectAttributes.addFlashAttribute`).

## 4. 화면별 명세

### 4-1. 게시글 목록 (`/`, `/posts`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 전체 공개 |
| 목적 | 최신 글을 페이지 단위로 훑어보고 상세로 진입 |
| 주요 요소 | 검색/정렬(선택), 글 카드 리스트(제목·작성자·작성일·미리보기 일부), 페이지네이션, (로그인 시) 글쓰기 버튼 |
| 빈 상태 | "아직 작성된 글이 없습니다. 첫 글을 남겨보세요." + (로그인 시) 글쓰기 버튼 |

```
┌───────────────────────────────────────────┐
│ [+ 글쓰기]                     (로그인 시만) │
├───────────────────────────────────────────┤
│ 제목 A                     작성자1  2026-08-20│
│ 본문 미리보기 한 줄...                        │
├───────────────────────────────────────────┤
│ 제목 B                     작성자2  2026-08-19│
│ 본문 미리보기 한 줄...                        │
├───────────────────────────────────────────┤
│              «  1  2  3  »                  │
└───────────────────────────────────────────┘
```

### 4-2. 게시글 상세 (`/posts/{id}`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 전체 공개 (수정/삭제 버튼만 조건부) |
| 주요 요소 | 제목, 작성자, 작성/수정일, 본문(자동 이스케이프 렌더링), 목록으로, (본인 글일 때만) 수정/삭제 버튼 |
| 권한 표시 | `sec:authorize`와 작성자 ID 비교로 **본인 글일 때만** 수정/삭제 버튼 렌더링. 다른 사람이 URL을 직접 조작해 `/posts/{남의 글 id}/edit`으로 들어오면 → 서버가 403을 반환하고 에러 페이지로 보낸다 (버튼 숨김은 UX일 뿐, 실제 차단은 서버) |
| 삭제 흐름 | 삭제 버튼 → 확인 모달("정말 삭제하시겠습니까?") → 확인 시 `DELETE /api/posts/{id}` 호출 → 성공 시 목록으로 리다이렉트 + flash 메시지 |

### 4-3. 게시글 작성 / 수정 (`/posts/new`, `/posts/{id}/edit`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 로그인 필요 (수정은 작성자 본인만) |
| 주요 요소 | 제목 입력(최대 200자, 남은 글자수 표시), 본문 textarea(필수), 저장/취소 버튼 |
| 검증 | 클라이언트 측 `required`/`maxlength`는 **UX 보조용**이며, 서버(Bean Validation `@NotBlank @Size`)가 최종 검증한다. 둘 중 하나만 있으면 안 됨(클라이언트만 있으면 curl로 우회 가능, 서버만 있으면 사용자 경험이 나쁨) |
| XSS 관련 UX | 본문에 `<`, `>` 등을 입력해도 막지 않는다(과도한 클라이언트 필터링은 정상적인 글쓰기를 방해함) — 대신 **출력 시점에 항상 이스케이프**되므로 저장은 자유롭게, 렌더링만 안전하게 ([01_기획.md 리스크 §10](01_기획.md#10-예상-난이도-및-리스크) 참고) |

### 4-4. 로그인 (`/login`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 비로그인만 (로그인 상태로 접근하면 목록으로 리다이렉트) |
| 주요 요소 | 아이디, 비밀번호, 로그인 버튼, 회원가입 링크 |
| 실패 표시 | "아이디 또는 비밀번호가 올바르지 않습니다" 통일 메시지 (계정 존재 여부 노출 금지) |
| CSRF | 폼에 `${_csrf.parameterName}` hidden input 자동 포함 (Thymeleaf `th:action` 사용 시 Spring Security가 자동 삽입) |

### 4-5. 회원가입 (`/signup`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 비로그인만 |
| 주요 요소 | 이메일, 아이디, 비밀번호, 비밀번호 확인, 가입 버튼 |
| 검증 | 이메일 형식, 비밀번호 규칙(최소 8자, 영문+숫자 — [01_기획.md §7](01_기획.md#7-보안-요구사항)), 비밀번호/확인 일치, 이메일·아이디 중복 여부(서버 최종 확인) |
| 성공 시 | 가입 완료 flash 메시지 + 로그인 화면으로 이동 (자동 로그인은 하지 않음 — MVP 범위 밖) |

### 4-6. 비밀번호 변경 (`/account/password`)

| 항목 | 내용 |
|---|---|
| 접근 권한 | 로그인 필요 |
| 주요 요소 | 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인 |
| 검증 | 현재 비밀번호가 실제 DB 해시와 일치하는지 서버에서 재확인 후에만 변경 허용 |

## 5. 공통 컴포넌트

| 컴포넌트 | 용도 |
|---|---|
| Flash 알림 | 성공(초록)/실패(빨강) 배너, 리다이렉트 후 1회 노출 |
| 확인 모달 | 삭제 등 되돌릴 수 없는 작업 전 확인 (Bootstrap Modal) |
| 페이지네이션 | Bootstrap `.pagination`, 서버의 `Pageable` 응답과 매핑 |
| 폼 에러 표시 | 필드 아래 빨간 텍스트로 Bean Validation 실패 메시지 표시 (`th:errors`) |

---

## 6. 접근성 체크리스트

- [ ] 모든 `<input>`에 연결된 `<label>` (placeholder만으로 대체하지 않음)
- [ ] 버튼/링크에 의미 있는 텍스트 (아이콘만 있는 버튼은 `aria-label` 추가)
- [ ] 폼 에러가 색상만이 아니라 텍스트로도 전달됨
- [ ] 키보드만으로 로그인 → 글쓰기 → 저장까지 전체 흐름 가능한지 확인 (4주차 검증 항목에 포함)
